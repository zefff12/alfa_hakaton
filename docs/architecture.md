# Архитектура

## Компоненты

```mermaid
flowchart LR
    subgraph Client["Браузер"]
        CAB["Кабинет клиента<br/>React + Альфик"]
        UW["Консоль андеррайтера<br/>React"]

    subgraph Edge["web (nginx)"]

    subgraph Core["Кредитный конвейер"]

        WRK["worker (×N)<br/>автоматические этапы<br/>FOR UPDATE SKIP LOCKED"]
        DB[("PostgreSQL<br/>заявки, аудит,<br/>документы, чат")]
        FS[("storage<br/>файлы документов")]
    end

    subgraph Ext["Внешние источники (моки)"]
        EGRUL["ЕГРЮЛ / ЕГРИП"]

    end

    LLM["Ollama + Qwen2.5<br/>(open weights, опционально)"]

    CAB --> NG
    UW --> NG
    NG --> API
    API --> DB
    API --> FS
    WRK --> DB
    API -- "автозаполнение по ИНН" --> EGRUL
    WRK -- "таймаут, ретраи,<br/>circuit breaker" --> EGRUL

    WRK --> BKI
    API -. "свободные вопросы" .-> LLM
```

| Сервис | Технологии | Назначение |
|---|---|---|
| `web` | React 19, TypeScript, Vite, nginx | SPA кабинета клиента и консоли банка; проксирует `/api` |
| `api` | Python 3.12, FastAPI, SQLAlchemy 2, Pydantic 2 | REST API, авторизация, машина состояний, ассистент, лента |
| `worker` | тот же образ, `python -m app.worker` | Автоматические этапы конвейера; масштабируется `--scale worker=N` |
| `db` | PostgreSQL 16 | Хранилище заявок, журнала аудита, документов, уведомлений, чата |
| `mocks` | FastAPI | Симуляторы ЕГРЮЛ/ЕГРИП, ФНС «Прозрачный бизнес», БКИ |
| `ollama` (профиль `llm`) | Ollama + Qwen2.5 3B | Локальная open-weights LLM для свободных вопросов Альфику |

## Слои бэкенда

```
backend/app
├── api/            HTTP-слой: auth, client (кабинет), bank (консоль)
├── services/       Сценарии: pipeline (конвейер), applications, assistant, intake (диалог), summary (резюме), feed
├── domain/         Чистая бизнес-логика без I/O:
│   ├── state_machine.py   статусы и разрешённые переходы по ролям
│   ├── scoring.py         балльная модель риска (scorecard)
│   ├── decision.py        кредитная логика: стоп-факторы, лимит, контрпредложение
│   ├── readiness.py       «Каковы мои шансы?» на той же модели
│   ├── advisor.py         подбор продукта под задачу
│   ├── intake.py          разбор свободного рассказа клиента в параметры заявки
│   ├── statement.py       разбор выписки 1С / CSV: очищенные обороты, концентрация
│   ├── calculator.py      аннуитет, обратный расчёт, график
│   └── products.py        каталог продуктов и документов
├── integrations/   HTTP-клиенты внешних сервисов (таймауты, ретраи, circuit breaker)
├── models.py       ORM-модель данных
└── worker.py       цикл обработки конвейера
```

Доменный слой не зависит от БД и HTTP — он покрыт модульными тестами и может переиспользоваться (например, для пересчёта решений или A/B-сравнения моделей).

## Ключевые технические решения

| Требование | Решение |
|---|---|
| Последовательная смена состояний | Единственная точка перехода `pipeline.transition()`: проверка по таблице переходов и роли, журнал аудита, уведомление |
| Конкурентный доступ | Оптимистическая блокировка (`version`) — 409 при изменении заявки в другой вкладке/другим участником |
| Горизонтальное масштабирование | Воркеры берут задачи через `SELECT … FOR UPDATE SKIP LOCKED`; API stateless (JWT) |
| Отказоустойчивость интеграций | Таймаут 2 с, 3 ретрая с экспоненциальной паузой, circuit breaker; недоступность источника → заявка уходит специалисту, а не «падает» |
| Сбой этапа | 3 повторные попытки с backoff, затем ручное рассмотрение с записью в аудит |
| Трассировка | `X-Request-ID` в каждом ответе и в логах, журнал событий по заявке |
| Безопасность | JWT + RBAC (клиент видит только заявки своей компании), PBKDF2-хеши паролей, лимиты и белый список типов файлов, SHA-256 документов, непривилегированные пользователи в контейнерах, внутренние правила скоринга не раскрываются клиенту |
| Наблюдаемость | `/health/live`, `/health/ready` (проверка БД), healthcheck'и в Docker, метрики конвейера `/api/bank/metrics` |
| Воспроизводимость | `uv.lock`, `package-lock.json`, фиксированные версии образов |
| Конфигурация | Только переменные окружения (12-factor), см. `.env.example` |

## Мультиязычность (RU / EN / 中文)

```mermaid
flowchart LR
    UI["Интерфейс: t('русский текст')<br/>словарь i18n-dict.ts"] -- "X-Lang: en | zh" --> MW["i18n-middleware API"]
    MW --> EP["эндпоинты формируют тексты на русском"]
    EP --> MW
    MW -- "перевод JSON по каталогу<br/>(точные строки + шаблоны)" --> UI
    TALK["Рассказ на EN / 中文"] --> NORM["intake_lang: нормализация<br/>2 million → 2 млн, 200万 → 2 млн"] --> PARSER["общий парсер intake.py"]
```

* **Сервер.** Тексты формируются на русском — так их видят андеррайтер и журнал аудита. Middleware переводит JSON-ответы кабинета клиента по каталогу `app/i18n/catalog.py`: около 350 точных строк и 60 шаблонов с подстановками, подстановки переводятся рекурсивно. Поэтому сохранённые в БД события, причины решений и уведомления показываются на выбранном языке без хранения копий. Данные пользователя и реквизиты не переводятся. Консоль банка (`/api/bank`) остаётся на русском.
* **Составные ответы**, которые собираются в самом запросе (чат Альфика, диалог «Расскажите Альфику»), формируются сразу на нужном языке через `L(ru, en, zh)`.
* **Понимание речи.** `domain/intake_lang.py` нормализует английский и китайский текст в канонические формы, включая китайские 万/亿 и цифры иероглифами, после чего работает общий, покрытый тестами парсер.
* **Клиент.** Функция `t("русский текст")`: ключ — сам русский текст, поэтому отсутствие перевода не ломает интерфейс. Деньги и даты форматируются через `Intl` по локали. Кодмод `scripts/i18n-codemod.cjs` обернул строки в `t()`, проверка `npm run i18n:check` следит за полнотой словаря.
* **Контроль качества.** Тест `test_full_journey_has_no_untranslated_text` проходит сквозной сценарий на EN и ZH и падает, если в ответе API осталась хотя бы одна русская строка интерфейса.

## Где используется ИИ и почему

| Задача | Подход | Почему так |
|---|---|---|
| Статус, причины решения, документы, расчёт платежа | Правила (intent-матчинг) | Ответ должен быть точным и проверяемым; LLM здесь создаёт риск ошибки |
| Свободные вопросы предпринимателя | Локальная LLM Qwen2.5 (Apache-2.0) с контекстом заявки | Понятная ценность: объяснить простыми словами; ограничения в промпте + пост-фильтр против обещаний одобрения |
| Заявка из рассказа («Расскажите Альфику») | Правила + словари (`domain/intake.py`), LLM дополняет только пропущенные поля | Числа и сроки должны разбираться детерминированно; каждое значение показано с фразой-источником, клиент подтверждает перед созданием черновика |
| Голосовой ввод | Web Speech API браузера | Встроенная функция Edge/Chrome, без сторонних сервисов в составе решения; при её отсутствии работает текстовый ввод |
| Разбор выписки | Парсер 1С «Клиент-Банк» и CSV (`domain/statement.py`) | Подтверждает обороты фактом, сокращает ручную проверку; PDF честно уходит специалисту |
| Резюме для андеррайтера | Детерминированная сборка из данных конвейера (`services/summary.py`) | Каждое утверждение проверяемо и опирается на конкретный источник |
| Скоринг | Прозрачная балльная модель | Объяснимость для клиента и андеррайтера, регуляторные требования |

Без LLM прототип полностью работоспособен — ассистент отвечает по базе знаний.
